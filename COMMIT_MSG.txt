All To DSD Core: FLAC/WAV -> DSF converter (JM21 All-To-DSD chain)

Standalone Windows converter implementing the FiiO JM21 player's
"All To DSD" digital processing chain. The chain was derived from the
device firmware and verified against the real hardware:

- 18 golden vectors x 3 layers (quantiser input / 1-bit intermediate /
  packed stream / DSF DATA): byte-exact across three independent
  implementations
- long-input production run (20 s, 3446 DSD blocks) structurally verified
- device analog-output spectrum experiment confirms the noise-shaping
  signature predicted by the digital model
- packed DSD64 stream accepted and correctly decoded by an independent
  DSD DAC (CS43131)

Usage and the verified parameter set are documented in README.md.
Source code is not included in this repository at this time.

Fix: the -r 64/128 WAV output path materialised the entire L-times-upsampled signal three times over (perCh, hi, and out = hi) plus a full-size scratch buffer inside the resampler -- 32.5 GiB measured peak working set for a 3.5 minute track, and the old binary died with std::bad_alloc on a plain command-line -r 128. That is what was killing the web server mid-conversion with an access violation. Both the interpolation and the decimation now run block by block through a StreamingDecimator that keeps only the last T-1 input frames, so peak memory scales with the output rate instead of the L-times-upsampled rate: 32550 MiB -> 824 MiB at -r 64, and -r 128 now completes at 950 MiB instead of failing. The DSP is unchanged -- each block still builds a fresh Jm21Core, exactly as before -- and the -r 64 output is byte-for-byte identical to the previous build (cmp, 78,941,954 B).

Also: symbolised crash reporting (SetUnhandledExceptionFilter + set_terminate writing exception code, fault address and a resolved backtrace to %TEMP%\flac2dsf-server.log), peak-working-set logging around every job, and the same job-state line in the crash report.

Fix: "file gone" on every download below DSD256, which was two defects stacked on the same path. (1) The job recorded o.out, but the WAV writer appends its own extension, so the download looked for "song.dsf" while the file was "song.dsf.wav"; Result now carries the path actually written and the job follows it, the extension is replaced rather than appended, and the UI labels the link with the real extension. (2) writeWav24() was the last writer in the program still using narrow fopen() instead of the UTF-8 wrapper f2d_fopen(), so it could not represent a CJK path on a GBK system at all -- every -r 64/128 conversion of a Chinese-named file failed with "cannot write". The DSF writer always used the wrapper, which is why only this path was affected.

Verified end to end with a CJK-plus-space filename at all three rates; the -r 64 download is byte-for-byte identical to the pre-fix reference.

Docs/UI: "DSD64" is 2,822,400 Hz of 1-bit audio, not 44.1 kHz -- 44.1 kHz is only one of two ways to factor that number, and the UI never said which one you were getting. The JM21 path factors it as 88.2 kHz x 32 (the device core always interpolates 32:1), the FIR path as 44.1 kHz x 64. Both are DSD64; for a 48 kHz source the JM21 one additionally keeps the 22.05-24 kHz band that a 44.1 kHz base cannot hold.

The preset notes now name the intermediate PCM rate, a live chain readout follows the rate and jm21 controls, and each finished job reports the chain it actually ran: source rate -> PCM rate on the chain -> 1-bit rate (or 24-bit WAV). Job also carries pcmRate, which was missing and made the WAV rows read "no 1-bit" without saying what rate the chain used.
